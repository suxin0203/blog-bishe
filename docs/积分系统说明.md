# 文栈博客积分系统说明

> 本文档用于说明当前项目中“积分如何产生、如何扣除、何时回退、每日上限如何计算”。
>
> 本文档以当前代码实现为准，目标是帮助开发者、维护者和后续联调人员快速理解积分系统的实际运行规则。

---

## 一、积分系统目标

积分系统用于增强博客平台的互动性与内容激励，核心思想如下：

1. 鼓励用户持续登录
2. 鼓励用户发布内容
3. 鼓励用户产出高质量评论
4. 鼓励优质内容获得点赞
5. 允许用户使用积分兑换商品或称号
6. 支持管理员人工修正积分

当前积分系统采用“**积分流水 + 用户当前积分余额**”的实现方式：

- `wz_users.points`：记录用户当前积分余额
- `wz_user_points_log`：记录每一次积分变动明细

也就是说：

- 用户当前积分 = 历史有效积分变化的累计结果
- 每次加分、扣分、回退，都会尽量写入一条积分流水

## 二、当前积分来源总览

当前项目已接入的积分来源如下：

| 场景 | 分值 | 是否有每日上限 | 说明 |
|------|------|----------------|------|
| 每日登录 | +5 | 有，每日 1 次 | 登录成功后发放 |
| 发布文章 | +10 | 有，每日最多 100 分 | 创建文章成功后发放 |
| 评论审核通过 | +5 | 有，每日最多 50 分 | 评论状态从未通过变为通过时发放 |
| 文章被点赞 | +1 | 无 | 给被点赞文章作者发放 |
| 取消点赞 | -1 | 无 | 回退被点赞文章作者的获赞积分 |
| 删除文章 | 扣回对应文章发布奖励 | 无 | 删除后尝试回退发布文章时拿到的积分 |
| 删除已通过评论 | 扣回对应评论审核奖励 | 无 | 删除后尝试回退评论通过时拿到的积分 |
| 积分兑换商品 | 扣减商品所需积分 | 无 | 创建兑换订单时扣除 |
| 管理员手动调整 | 正负都可 | 无 | 后台手动加减分 |
| 退款 | 视业务逻辑而定 | 无 | 当前文案已保留 reason，但是否触发取决于具体退款流程 |

## 三、积分流水存储方式

### 1. 当前余额

用户当前积分存储在：

- `wz_users.points`

### 2. 流水表

积分变动明细存储在：

- `wz_user_points_log`

每条流水至少包含：

- `user_id`
- `change`：本次变动值，正数代表加分，负数代表扣分
- `reason`：本次积分变化原因
- `created_at`

### 3. 当前使用的主要 reason

当前代码中已经使用或兼容了以下 reason：

| reason | 含义 |
|--------|------|
| `daily_login` | 每日登录 |
| `comment` | 旧版评论积分 reason，历史兼容保留 |
| `like` | 旧版点赞积分 reason，历史兼容保留 |
| `like_cancel` | 旧版取消点赞 reason，历史兼容保留 |
| `article_liked:{articleId}:{title}` | 文章获赞 |
| `article_unliked:{articleId}:{title}` | 文章取消获赞 |
| `article_publish:{articleId}:{title}` | 发布文章 |
| `article_delete:{articleId}:{title}` | 删除文章后回退发布奖励 |
| `comment_approved:{commentId}:{articleTitle}` | 评论审核通过 |
| `comment_removed:{commentId}:{articleTitle}` | 删除已通过评论后回退奖励 |
| `redeem_goods` | 积分兑换商品 |
| `refund` | 退款 |
| `admin_adjust:备注` | 管理员调整积分 |

### 4. 前端展示方式

前端会把带参数的 `reason` 解析成更易读的文案，例如：

- `article_liked:12:Vue3 入门` → `文章获赞《Vue3 入门》`
- `article_unliked:12:Vue3 入门` → `文章取消获赞《Vue3 入门》`
- `article_publish:9:博客部署指南` → `发布文章《博客部署指南》`
- `comment_approved:31:SpringBoot 教程` → `评论审核通过《SpringBoot 教程》`

## 四、各积分场景详细规则

## 4.1 每日登录积分

### 规则

- 用户登录成功后，可获得 `+5` 积分
- 同一用户同一天只允许获得一次

### reason

- `daily_login`

### 说明

这是一个典型的“每日一次”奖励型积分，不支持同日重复领取。

---

## 4.2 发布文章积分

### 规则

- 用户成功创建文章后，给予 `+10` 积分
- 同一用户同一天在“发布文章”这一类积分上，**累计最多 100 分**

### reason

- 发放：`article_publish:{articleId}:{title}`
- 回退：`article_delete:{articleId}:{title}`

### 每日上限说明

系统按 reason 前缀 `article_publish:` 统计当天正向积分总和。

例如：

- 第 1 篇文章：+10
- 第 2 篇文章：+10
- ...
- 当天累计达到 100 后，继续发文不再继续加这类积分

### 删除时的处理

当前实现中：

- 删除文章后，会尝试查找该文章对应的发布积分记录
- 如果找到对应正向奖励记录，则写入一条负向流水，扣回对应积分

### 注意事项

1. 当前逻辑是“**删除扣回发布奖励**”
2. 当前文档所说“删除”包括：
   - 软删除（进入回收站）
   - 硬删除（彻底删除）
3. 当前实现更偏向“内容被删除即视为不再保留发布奖励”

---

## 4.3 评论审核通过积分

### 规则

- 用户发表评论时，默认先进入待审核状态
- 当评论状态从“未通过”变成“已通过”时，评论作者获得 `+5` 积分
- 同一用户同一天在“评论审核通过”这一类积分上，**累计最多 50 分**

### reason

- 发放：`comment_approved:{commentId}:{articleTitle}`
- 回退：`comment_removed:{commentId}:{articleTitle}`

### 每日上限说明

系统按 reason 前缀 `comment_approved:` 统计当天正向积分总和。

例如：

- 第 1 条审核通过评论：+5
- 第 2 条审核通过评论：+5
- ...
- 当天累计达到 50 后，继续审核通过也不会再继续发这类积分

### 何时发放

只在下面条件同时满足时发放：

1. 原评论状态不是 `1`
2. 更新后评论状态变成 `1`
3. 评论存在有效用户 `user_id`

因此不会因为重复点击“通过”而无限重复加分。

### 删除时的处理

如果删除的是“已通过评论”，系统会：

1. 尝试查找该评论对应的审核奖励记录
2. 如果找到对应记录，则写入一条负向积分流水，扣回对应积分

---

## 4.4 文章获赞积分

### 规则

- 点赞者自己**不加积分**
- 被点赞文章的作者获得 `+1` 积分
- 取消点赞时，文章作者 `-1`
- 自己点赞自己的文章，不产生积分

### reason

- 发放：`article_liked:{articleId}:{title}`
- 回退：`article_unliked:{articleId}:{title}`

### 设计原因

当前项目采用“奖励内容生产者，而不是奖励点赞操作人”的规则，原因如下：

1. 更符合博客社区逻辑
2. 更能鼓励写作者产出内容
3. 能减少互赞刷分问题
4. 避免“我去点别人赞，自己涨分”的不合理情况

### 取消点赞时的处理

- 若之前点赞确实给作者加过分，取消点赞时会给作者扣回 1 分

### 边界说明

- 同一用户对同一文章不能重复点赞加分，因为点赞关系表会约束这一行为
- 取消后再次点赞，属于新的有效点赞，会再次给作者加分
- 文章作者为空或用户已注销时，不发放该类积分

---

## 4.5 积分兑换商品

### 规则

- 用户在积分商城发起兑换时，若积分足够，则直接扣除对应积分
- 同时写入积分流水

### reason

- `redeem_goods`

### 说明

该类积分为直接消费型积分，不属于奖励积分。

---

## 4.6 管理员人工调整积分

### 规则

- 管理员可在后台对用户积分做人工加减
- 支持正数和负数
- 建议填写备注

### reason

- `admin_adjust:备注`

### 前端展示

前端会把它展示成：

- `管理员调整：xxx`

---

## 五、每日上限的实现方式

当前项目没有单独的“积分规则表”，而是采用较轻量的实现：

### 1. 按 reason 前缀统计当天正向积分

例如：

- `article_publish:` 这一类，统计当天正向总和
- `comment_approved:` 这一类，统计当天正向总和

### 2. 发分时做截断

例如用户今天已经拿到：

- 文章发布积分 95 分

那么再发布一篇文章时：

- 本应加 10
- 但当天只剩 5 分空间
- 实际发放 5 分

也就是说，当前实现支持“**按剩余额度发放**”，不是简单地超限后整条丢弃。

---

## 六、删除与回退规则

为了让积分系统更严谨，当前实现引入了“删除回退”规则。

### 1. 删除文章

- 如果该文章在创建时拿到过发布积分
- 删除时会尝试扣回这条奖励

### 2. 删除已通过评论

- 如果该评论在审核通过时拿到过积分
- 删除时会尝试扣回这条奖励

### 3. 取消点赞

- 如果点赞时给文章作者加过分
- 取消点赞时会扣回 1 分

### 4. 当前未实现的恢复返还

当前代码**尚未实现**以下完整闭环：

- 恢复文章后，自动返还发布积分
- 恢复评论后，再自动返还评论奖励

因此当前规则更接近：

- **新增有奖励**
- **删除有回退**
- **恢复暂不自动补回**

如果后续要让回收站逻辑更完整，可以继续补充“恢复返还积分”。

## 七、与用户状态的关系

### 1. 停用用户

当前系统中：

- `wz_users.status = 0` 表示正常
- `wz_users.status = 1` 表示停用

停用用户会被限制登录和受保护接口访问。

### 2. 积分影响

当前实现没有专门在所有积分入口再次判断“停用用户是否允许继续累积积分”，但由于停用用户本身无法正常登录和操作后台/互动接口，因此大多数积分入口会被自然阻断。

如果后续要做得更严格，可以在积分服务层统一补一层“停用用户不可再新增积分”的兜底检查。

## 九、当前实现的优点

### 1. 逻辑相对严谨

- 点赞奖励给作者而非点赞者
- 评论审核通过才加分
- 删除时支持回退
- 每日上限生效

### 2. 改动成本小

- 不需要新增复杂积分规则表
- 不需要新增单独结算任务
- 复用现有积分流水表即可运行

### 3. 可读性提升

- 积分流水已能展示具体文章标题
- 管理和排查问题更方便

## 十、当前实现的限制与后续建议

虽然当前实现已经可用，但仍有一些可继续优化的地方：

### 1. 删除回退匹配仍偏轻量

当前是通过 `reason` 中的业务标识和标题来识别对应奖励记录。

这对当前项目已经够用，但如果后续业务更复杂，建议引入更稳定的“业务对象 ID + 积分事件类型”绑定机制。

### 2. 恢复返还积分尚未闭环

建议后续补充：

- 文章恢复时是否返还发布积分
- 评论恢复并重新通过时是否返还积分

### 3. 可进一步统一旧版历史 reason

当前系统为了兼容旧流水，保留了：

- `like`
- `like_cancel`
- `comment`

未来若要进一步统一，可考虑：

- 只保留新的业务化 reason
- 历史数据做迁移或在前端继续兼容展示

### 4. 可增加更严格的风控限制

例如：

- 限制同一用户对同一作者每天可贡献的获赞积分
- 停用用户禁止新增积分流水
- 更精细的评论刷分控制

## 十一、推荐理解顺序

如果你要继续维护积分系统，建议按下面顺序理解代码：

1. `Express/services/pointsService.js`
   - 积分流水写入
   - 每日上限统计
   - 流水解析

2. `Express/services/articleLikeService.js`
   - 文章获赞积分逻辑

3. `Express/controllers/articleController.js`
   - 发布文章积分
   - 删除文章回退积分

4. `Express/controllers/commentController.js`
   - 评论审核通过积分
   - 删除评论回退积分

5. 前端积分展示页面
   - `Vue3/src/views/MyPointsLog.vue`
   - `Vue3/src/views/dashboard/Dashboard.vue`
   - `Vue3/src/views/dashboard/Users.vue`

---

## 十二、当前建议采用的业务口径

如果后续需要对外说明“本系统积分规则是什么”，建议统一口径如下：

1. 每日登录可获得积分
2. 发布文章可获得积分，设有每日上限
3. 评论审核通过可获得积分，设有每日上限
4. 文章被点赞时，作者可获得积分
5. 删除文章、删除已通过评论、取消点赞时，会回退对应积分
6. 积分可用于积分商城兑换
7. 管理员可手动调整积分
