## 文栈博客系统核心技术与安全机制

### 1. 整体技术栈与架构

- **前端技术栈**：基于 `Vue 3 + Vite + Naive UI + Pinia` 构建单页面应用，使用 Axios 封装统一请求与响应拦截，在路由层实现后台管理权限控制。
- **后端技术栈**：基于 `Node.js + Express` 实现 RESTful API，采用「路由层（routes）→ 控制器层（controllers）→ 服务层（services）→ 数据访问层（common/utils + mysql2/promise）」的分层结构，业务逻辑清晰可维护。
- **数据库与持久化**：使用 MySQL 8.0 作为数据存储，`mysql2` 连接池负责连接管理，所有数据库操作通过参数化查询执行，避免拼接 SQL。
- **接口风格**：后端统一返回 `{ code, message, data }` 格式，错误通过统一错误处理中间件转化为 JSON 响应，并提供 Swagger（`/api-docs`）文档用于接口调试与说明。

### 2. 用户认证与权限控制

- **密码存储（bcrypt 哈希）**  
  - 后端在 `userController` 中使用 `bcrypt` 对用户密码进行哈希存储，`saltRounds` 设置为 **10**：  
    - 注册、管理员添加用户、修改密码、找回密码均通过 `bcrypt.hash(明文密码, 10)` 生成哈希后写入 `wz_users.password`。  
    - 登录、修改密码时通过 `bcrypt.compare(输入密码, 数据库存储哈希)` 校验，避免明文密码在服务器端出现。  
  - bcrypt 内置随机盐机制，有效防御彩虹表攻击和简单暴力破解。

- **密码传输保护（前端 Base64 编码）**  
  - 前端通过 `encode.js` 中的 `base64Encode` 对密码进行 Base64 编码后再提交，后端在 `userController.decodePassword` 中统一尝试 Base64 解码；  
  - 这样可以避免在抓包时直接看到可读明文（仍需在实际部署中配合 HTTPS 使用）。

- **图形验证码防爆破**  
  - 登录、注册等敏感操作前需通过简单算术验证码校验：  
    - 后端生成 `num1 + num2` 的答案临时保存在内存 `captchaStore`，设置 5 分钟有效期。  
    - 前端将验证码答案经 MD5（`captchaMd5`）处理后提交，后端对比 MD5 值并在一次验证后删除，避免重复使用。  
  - 该机制减少了账号被穷举或脚本暴力登录的风险。

- **JWT 无状态认证与刷新机制**  
  - 登录成功后，后端基于 `jsonwebtoken` 生成两类 Token：  
    - **访问 Token**：有效期 2 小时，载荷包含 `id、username、is_root、role`，用于日常鉴权。  
    - **刷新 Token**：有效期 7 天，仅包含 `{ id, type: 'refresh' }`，用于在访问 Token 过期后无感刷新。  
  - 刷新 Token 会被写入数据库 `wz_users.refresh_token` 与 `refresh_token_expires_at`，每次刷新时后端会校验：  
    - JWT 签名与过期时间；  
    - 数据库中是否存在该 refreshToken 且未过期；  
    - Token 类型是否为 `refresh`。  
  - 前端 Axios 响应拦截器在收到业务 `code = 401` 或 HTTP 401 时，会自动调用 `/users/refresh`：  
    - 若刷新成功，更新本地 `token` 与用户信息，并重发原请求；  
    - 若刷新失败或 refreshToken 失效，则清除本地登录状态并提示用户重新登录。  
  - 整体流程实现了 **无 Session 的 JWT 认证 + 可控的长登录体验**，并通过数据库保存 refreshToken 防止被盗后长期滥用。

- **基于角色的权限控制（RBAC）**  
  - JWT 载荷中包含 `is_root` 与 `role`（`admin/editor/user`），后端在 `/token` 前缀路由中间件中统一校验：  
    - 管理员（`is_root=1`）和编辑（`role=editor`）可访问后台管理相关接口；  
    - 普通用户仅能访问自身资料更新、点赞/收藏等有限 `/token` 接口；  
    - 未携带 `Authorization` 头或 Token 校验失败/过期时返回业务 `code=401` 或 `code=403`。  
  - 前端路由与组件侧也根据用户角色隐藏无权限菜单项，前后端共同保证权限边界。

### 3. 请求安全与防重放机制

- **时间戳防重放（X-Request-Time）**  
  - 前端 Axios 请求拦截器在每次发起请求时，自动在请求头中加入 `X-Request-Time` 毫秒级时间戳。  
  - 后端全局中间件读取 `X-Request-Time`，当该头存在时：  
    - 将其解析为整数，与服务器当前时间 `Date.now()` 求绝对差值；  
    - 若时间差超过 **30 秒** 或解析失败，则直接返回 `{ code: 400, message: '请求已过期或时间偏差过大，请同步系统时间后重试' }`，不再继续后续处理。  
  - 该机制可以有效拦截延迟过长或被重放的请求，在一定程度上降低重放攻击风险（在实际部署中可结合 HTTPS 与更严格签名策略进一步加强）。

- **统一 CORS 与日志记录**  
  - 通过 `cors` 中间件统一开启跨域访问，确保前端在不同域名/端口下正常调用接口；  
  - 使用 `morgan` 记录请求日志，便于追踪异常请求与安全审计。

### 4. 数据访问安全：参数化查询与输入校验

- **参数化 SQL 查询**  
  - 数据访问层统一通过 `runQuery(sql, values)` 调用 `mysql2` 的预处理参数机制：  
    - SQL 语句中的变量一律使用 `?` 占位，并在 `values` 数组中传递真实参数；  
    - 数据库驱动负责对参数进行转义与绑定，有效防止经典的 SQL 注入（例如 `' OR 1=1 --` 等注入语句不会被直接拼进 SQL）。  
  - 用户模块（`userService`）、文章模块、评论模块、积分模块等均遵循此模式，避免手写字符串拼接 SQL。

- **业务层输入校验与字段白名单**  
  - 用户注册、登录、修改密码等接口对用户名、邮箱、密码长度与格式进行校验，防止异常输入穿透到数据库层；  
  - 更新用户信息时，服务层为可更新字段设置白名单，只允许 `nickname、avatar_url、email、status、role、points、title` 等有限字段进入 `SET` 子句，避免任意字段被修改。  
  - 对邮箱格式、角色字段等也做了额外限制，进一步提升数据安全与一致性。

### 5. 内容安全与评论审核

- **评论敏感词过滤与审核流**  
  - 评论模块在写入数据库前会根据系统配置表中的敏感词列表，对评论内容进行替换（将敏感词替换为 `***`），然后以「待审核」状态入库；  
  - 管理员在后台审核通过后，评论才会在前台页面展示，构成「提交 → 过滤 → 待审 → 发布/屏蔽」闭环流程。  
  - 该机制在数据库层面记录审核结果，对于攻击性、违规内容具备可追溯性。

- **XSS 防护（以渲染转义为主）**  
  - 前端在渲染用户评论等普通文本内容时，对 HTML 特殊字符进行转义（例如在测试中验证 `<script>alert(1)</script>` 不会被浏览器执行），减少存储型/反射型 XSS 风险。  
  - 富文本文章内容由于允许包含 HTML，由后台受信任角色（管理员/编辑）发布，不对其做 HTML 级别的自动转义，而是依赖发布者可信与后台审核。  
  - 在论文与测试章节中对「XSS 转义」的描述，主要对应**评论等用户输入内容的转义渲染**，而非对所有富文本字段进行 HTML 清洗。

> 需要说明的是：系统目前主要通过「前端转义渲染 + 受信任后台角色」来控制 XSS 风险，尚未引入例如 DOMPurify 之类的专门富文本清洗库，后续可以在文章与留言模块中进一步增强 HTML 级别的安全过滤。

### 6. 文件上传与资源访问安全

- **Multer 文件上传中间件**  
  - 后端使用 `multer` 将上传的图片等文件保存到 `public/upload/Filerelay/` 目录，统一通过 Express 静态资源中间件对外提供访问。  
  - 上传接口仅对具有相应权限的后台用户开放（例如文章封面、轮播图、头像等），避免任意用户随意上传文件。

- **静态资源与错误页面**  
  - Express 使用 `express.static` 托管静态资源，对访问错误的请求通过统一错误处理中间件返回 JSON 或错误页，同时不会泄露内部堆栈信息。  
  - 错误页面中的前端脚本只做页面倒计时重定向，不涉及动态拼接外部输入，避免进一步引入 XSS 风险。

### 7. 安全测试与验证

- 在系统测试阶段，针对以下安全能力进行了验证：  
  - **时间戳防重放**：构造 `X-Request-Time` 偏差大于 30 秒的请求，后端按预期返回「请求已过期或时间偏差过大」。  
  - **JWT 及刷新机制**：使用伪造 Token、过期 Token、过期 refreshToken 访问受保护接口，均被正确拒绝或要求重新登录。  
  - **SQL 注入防护**：在查询、搜索等参数中注入 SQL 片段，后端未出现注入成功的情况。  
  - **XSS 攻击场景**：在评论内容中注入脚本标签，前端渲染时不会执行恶意脚本。  
  - **密码安全**：抓包可见密码已通过 Base64 编码传输，数据库中仅保存 bcrypt 哈希值。

综合来看，文栈博客系统在「身份认证与授权」「请求防重放」「数据访问安全」「内容安全」等方面形成了多层次的防护体系，既保证了普通用户的使用体验，又兼顾了后台运营与数据安全需求。
