## 1. 整体技术架构

### 1.1 前端技术栈

- Vue 3
- Vite
- Naive UI
- Pinia
- Vue Router
- Axios
- WangEditor
- Prism.js
- ECharts
- CryptoJS
- Animate.css

### 1.2 后端技术栈

- Node.js
- Express
- MySQL
- mysql2
- jsonwebtoken
- bcrypt
- multer
- swagger-jsdoc
- swagger-ui-express
- cors
- morgan

### 1.3 架构模式

系统采用前后端分离架构：

- 前端负责页面渲染、状态管理与交互控制
- 后端负责接口、鉴权、业务逻辑、文件上传与数据库读写
- MySQL 负责业务数据持久化

后端整体遵循以下分层思路：

- `routes`：定义接口入口
- `controllers`：处理请求与参数
- `services`：封装业务逻辑
- 数据访问层：基于 `mysql2` 执行参数化 SQL

## 2. 请求处理链路

### 2.1 前端请求流程

1. 用户在页面上触发操作
2. Vue 组件调用 API 封装方法
3. Axios 请求拦截器统一附加请求头
4. 请求发送到 Express 后端
5. 响应返回后由 Axios 响应拦截器统一处理
6. 页面根据响应结果更新状态与界面

### 2.2 后端请求流程

1. Express 接收请求
2. 经过全局中间件：
   - CORS
   - 时间戳防重放
   - 文件上传处理
   - JSON / 表单解析
3. 根据路径进入对应路由
4. 若路径包含 `/token`，进入 JWT 鉴权与角色判断
5. 控制器调用服务层处理业务
6. 服务层执行数据库操作
7. 返回统一 JSON 响应：`{ code, message, data }`

### 2.3 统一返回机制

系统统一采用 JSON 返回：

- 成功：`{ code: 200, message, data }`
- 未登录 / Token 异常：`401`
- 权限不足：`403`
- 接口不存在：`404`
- 业务参数或时间戳异常：`400`

## 3. 身份认证机制

### 3.1 图形验证码

登录、注册等关键操作前，系统可通过验证码进行防刷与防爆破校验：

- 后端生成算术验证码
- 前端对答案做 MD5 处理后提交
- 后端进行一次性校验，成功后立即销毁

这可以降低恶意脚本批量尝试账号密码的风险。

### 3.2 密码处理机制

系统的密码安全分为两层：

#### 1）传输阶段
- 前端会对密码做 Base64 编码再发送
- 这并不是严格意义的加密，因此实际部署仍应配合 HTTPS

#### 2）存储阶段
- 后端使用 `bcrypt` 对密码进行哈希存储
- 注册、找回密码、管理员加人、修改密码等流程都不落明文密码
- 登录时通过 `bcrypt.compare()` 进行比对

### 3.3 JWT 访问令牌

登录成功后，后端会签发访问 Token：

- 访问 Token 用于后续接口鉴权
- 载荷一般包含：`id`、`username`、`is_root`、`role`
- 前端在访问受保护接口时，通过 `Authorization: Bearer <token>` 携带

### 3.4 Refresh Token 刷新机制

系统还提供刷新 Token 机制，用于提升登录体验：

- 登录成功后同时下发 `refreshToken`
- 刷新 Token 会保存到数据库中
- 当前端收到 401 时，可调用 `/users/refresh` 请求新访问 Token
- 刷新成功则重发原请求
- 若刷新失败，则清除登录态并要求重新登录

这一机制兼顾了：

- JWT 的无状态访问特性
- 用户较长时间保持登录的体验
- 刷新凭据可控、可过期、可失效的安全需求

## 4. 权限控制机制（RBAC）

### 4.1 路由级权限入口

后端在 `Express/app.js` 中对路径包含 `/token` 的请求统一进行鉴权。

处理逻辑如下：

1. 检查是否存在 `Authorization`
2. 解析并校验 JWT
3. 判断当前角色是否有权限执行该接口
4. 若无权限，返回 403

### 4.2 角色划分

系统当前主要存在三类角色：

- 管理员：`is_root = 1`
- 编辑：`role = editor`
- 普通用户：`role = user`

### 4.3 权限规则

#### 管理员 / 编辑
可访问后台管理类接口，例如：
- 文章、分类、标签管理
- 评论与留言管理
- 数据看板
- 上传、轮播、友链、系统设置
- 积分商品与订单后台接口

#### 普通用户
仅允许访问有限的受保护接口：
- 点赞接口：`/likes/token/...`
- 收藏接口：`/favorites/token/...`
- 修改本人资料：`PUT /users/token/:id` 且目标 id 必须是本人

### 4.4 可选 Token 解析

系统也支持“非强制登录接口的可选登录态识别”：

- 若请求不属于 `/token` 路径
- 但前端主动携带了 `Authorization`
- 后端会尝试解析 Token，并把用户信息写入 `req.user`

这对于“详情页展示当前用户是否点赞/收藏”等场景很有帮助。

## 5. 请求安全机制

### 5.1 时间戳防重放

系统支持通过 `X-Request-Time` 请求头实现轻量级防重放校验。

流程如下：

1. 前端在发送请求时附带毫秒级时间戳
2. 后端读取该头并与服务器当前时间比较
3. 若时间差超过 30 秒，直接拒绝请求

返回示例：

- `code = 400`
- `message = 请求已过期或时间偏差过大，请同步系统时间后重试`

这可以在一定程度上减少重放请求和长延迟请求带来的风险。

### 5.2 日志与跨域支持

- `cors` 负责跨域访问控制
- `morgan` 负责记录请求日志

这两者共同支持联调、排障与基础审计。

## 6. 数据访问安全

### 6.1 参数化查询

系统通过 `mysql2` 执行参数化 SQL：

- SQL 中使用 `?` 占位符
- 参数通过数组传入
- 避免手工拼接 SQL 字符串

这样可以有效降低 SQL 注入风险。

### 6.2 输入校验与字段白名单

在用户、文章、评论等模块中，业务层会对关键字段做限制，例如：

- 用户名长度
- 密码长度
- 邮箱格式
- 可更新字段白名单
- 角色字段合法性

这有助于避免异常输入直接进入数据库。

## 7. 内容安全机制

### 7.1 评论审核机制

评论提交后，不一定立即公开，而是进入审核流：

- 新评论写入数据库
- 根据规则进入待审核状态
- 管理员或具备权限的角色在后台审核
- 通过后才在前台展示

这一机制有利于控制垃圾评论、违规内容和恶意信息。

### 7.2 敏感词处理

系统支持在评论相关场景中接入敏感词过滤能力：

- 从系统配置中读取敏感词列表
- 对评论内容执行替换或拦截
- 过滤后再进行入库或审核

### 7.3 XSS 风险控制

在普通用户输入内容的展示场景中，系统主要依靠以下方式降低 XSS 风险：

- 文本内容按普通文本渲染
- 富文本发布权限交由受信任后台角色掌控
- 用户评论等高风险内容经过审核后再展示

这是一种“角色可信 + 审核控制 + 渲染约束”的组合策略。

## 8. 文件上传与静态资源机制

### 8.1 文件上传

系统通过 `multer` 处理文件上传：

- 上传内容落地到 `public/upload/Filerelay/`
- 后端统一接管上传请求
- 上传接口通常要求后台权限

### 8.2 静态资源访问

系统通过 `express.static` 提供静态资源访问能力：

- 图片上传后可被前端直接访问
- 便于富文本图片、轮播图等资源展示

## 9. API 文档与工程化能力

### 9.1 Swagger 文档

系统已接入 Swagger：

- 文档入口：`/api-docs`
- JSON 入口：`/api-docs.json`

这有助于：

- 前后端联调
- 接口核对
- 测试与演示
- 论文或答辩时展示接口体系

### 9.2 统一错误处理

系统对错误采用统一 JSON 输出方式：

- 路由不存在时返回 404 JSON
- 业务异常统一转换为结构化错误响应
- 避免将内部堆栈直接暴露给前端

## 10. 扫码登录相关技术点

虽然扫码登录有独立专题文档，但从技术角度看，它复用了现有系统能力：

- JWT 登录态签发
- 微信 openid 获取
- MySQL 会话存储
- PC 轮询机制
- 小程序端注册 / 绑定 / 确认登录流程

因此它本质上是对“认证体系”的扩展，而不是完全独立的一套登录系统。
